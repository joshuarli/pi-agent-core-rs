# Default profile parity evidence

`default-profile.json` is the exact generated prompt and tool-definition capture for the pinned
Pi coding-agent SDK. It is generated by [`../upstream/profile-runner.mts`](../upstream/profile-runner.mts)
from SDK source imports; it does not invoke the `pi` executable.

From `parity/upstream/source`, install the pinned lockfile dependencies and run the source-backed
verification:

```text
npm ci --ignore-scripts
./node_modules/.bin/tsx ../profile-runner.mts > ../../profile/default-profile.json
./node_modules/.bin/tsx ../../profile/verify-profile.mts
```

Run the complete default-profile source gate from the repository root:

```text
bash parity/run-profile.sh
```

`verify-profile.mts` proves all of the following against the checked-out source:

- the upstream commit/package pin and every source hash in `source-manifest.json`;
- active factory order (`read`, `bash`, `edit`, `write`);
- all seven standard definition objects, including metadata, prompt contributions, schema JSON,
  schema byte hashes, and schema serialization order;
- the complete default prompt after replacing only the three documented installation paths, plus
  its UTF-8 SHA-256 hash.

It also runs the direct virtual-operation evidence capture for `read`, `bash`, `edit`, `write`,
`find`, and `ls`. Those six cases import their pinned factories and validate success,
invalid-input, and host-operation-failure behavior against in-memory adapters. They do not
instantiate an Agent, read a workspace, invoke a shell, access credentials, or contact a model
provider.

`behavior-manifest.json` is the companion capture design for executable standard-tool parity. It
names the explicit operation-adapter methods and requires success, invalid-input, and host-error
cases for every standard tool. The behavior runner should create a temporary fixture workspace,
inject only the listed adapter, record operation calls and terminal tool-result fields, and run
the cases independently. Schema rejection must remain distinguishable from an adapter failure;
neither case may consult ambient cwd, HOME, `.pi`, sessions, credentials, or a provider.

Pinned upstream `grep` deliberately falls outside that virtual boundary: it resolves `rg` and
spawns it before calling `GrepOperations`. `verify-grep-process.mts` is therefore a separate,
explicit process-seam check. It creates an empty temporary `PI_CODING_AGENT_DIR` before importing
the pinned source, requires resolution to the process-PATH `rg` binary (never `~/.pi`), and runs
success, invalid-input, and missing-path cases in a disposable workspace. It does not invoke the
Pi executable or a model provider. A host without `rg` fails the verification rather than
downloading a managed binary.
