# V1 — Luau extension foundation

V1 is implemented. It adds a small, optional, capability-scoped Luau plane to
the completed Rust agent runtime. Its durable rule is:

> Rust owns mechanism, state, and effects. Luau owns local policy and
> composition. The embedding explicitly supplies every capability.

`pi-agent-core` neither depends on `mlua` nor constructs a VM. The optional
`pi-agent-luau` crate uses the pinned `mlua` `luau-jit` backend; no part of the
workspace uses Tokio. Embeddings remain responsible for driving all futures on
their chosen executor (Smol in the Runebench host).

## Delivered contract

### Closed bundles and deterministic authority

`bundle::Bundle` is an ABI-v1 collection of an explicit manifest and
canonical source records. The host supplies its bytes; the crate intentionally
does not search a cwd, `HOME`, package registry, filesystem, or network.
`BundleRuntime` gives each VM a fresh cache and accepts only `./` and `../`
imports that resolve inside that bundle. It rejects bare package names,
absolute paths, virtual modules not supplied by the host, cycles, and missing
modules. A source hash covers the manifest and every module deterministically.

`capability::CapabilityManifest` is a separate, serializable ABI-v1 authority
contract. It has typed `@agent`, `@world`, `@trace`, `@task`, `@json`, and
`@time` operation families, with exact server/method/target scoping for MCP.
`CapabilityGate` checks a requested operation before calling a host provider;
there are no wildcards or ambient fallbacks. A manifest describes authority—it
does not by itself install a Rust object into a VM.

### Policy and coroutine-backed tools

`LuaPolicy` continues to load a declarative policy table with a prompt suffix,
tool declarations, and a pre-tool allow/block/terminate decision. It also
loads a closed multi-module bundle through `LuaPolicy::load_bundle`.

A declared tool may include `handler_source`. The source evaluates to a Luau
function and is inert until the host deliberately builds a
`tool_handler::LuaToolHandler`. That adapter is an ordinary core `AgentTool`:
the core still owns schemas, preparation, scheduling, updates, ordering,
result insertion, cancellation, and settlement.

The handler may suspend only by yielding this exact table:

```luau
{
  kind = "capability",
  capability = "host-bound-name",
  method = "host-defined-method",
  arguments_json = "{...}"
}
```

`CapabilityBindings` contains only host-installed implementations. The
adapter rejects another capability name, malformed JSON, unbound capability,
and denied method with typed core errors. Each invocation owns a fresh,
sandboxed LuauJIT VM and has finite source, memory, interrupt, and host-call
budgets. Its one coroutine is structural, not an advisory limit. Cancellation
wakes the adapter even while its host future is permanently pending and drops
that pending future before settling.

### General caller-driven async bridge

For non-tool integrations, `async_runtime` installs an `await` request helper
and exposes `LuauAsyncRuntime`/`LuauTask`. It uses ordinary Luau coroutine
yields and caller-polled Rust futures instead of `mlua`'s executor-selecting
async feature. The embedding owns `HostAwaiter`, cancellation, and any I/O;
the task has at most one pending host future and drops it on cancellation.

### Isolation and evidence

The sandbox exposes only table, string, UTF-8, math, and coroutine facilities.
It has no `os`, `io`, package loader, debug API, ambient process/filesystem,
environment, clock, network, native FFI, or mutable shared globals. The
adversarial suite covers these denials, global mutation, source/memory/
interrupt limits, recursion/loop containment, error recovery, deterministic
declarations, and inter-policy isolation. The release benchmark measures VM
startup/teardown, hook latency, and 256 isolated policies without timing
thresholds.

Runebench is the first end-to-end embedding: its model-visible game tools are
declared in Luau and adapted into Rust `LuaToolHandler`s. A Rust-owned,
long-lived stdio MCP client is the sole `rs-agent` capability; its manifest
allows only the five exact game-tool/resource operations. The former
TypeScript MCP client bridge is not part of that path.

## Intentional boundaries

- A declaration, manifest entry, or capability-shaped string never creates an
  effect. The embedding must install and authorize the Rust capability.
- The shipped Luau surface is deliberately low-level. `@world`-style ergonomic
  modules are a host API design exercise, not an ambient default; an embedding
  may expose them only through the same explicit yield/gate boundary.
- Luau syntax (including annotations) is compiled by the embedded VM. This
  repository does not add a separate `luau-analyze` dependency or claim an
  external static type-check gate.
- Agent spawning, world forking, queues, trace persistence, sessions, a TUI,
  and plugin discovery remain Rust/host responsibilities. No swarm framework
  or package registry is introduced by V1.
